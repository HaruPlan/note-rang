# UI 문자열(i18n) 규약

**기준 언어인 한국어(ko)만 코어에 내장**한다(`src/i18n/ko.json`). **영어(en)는 번들
언어팩**이다 — `src/plugin/builtin/language-packs/language-pack-en/`이 외부 언어팩과
바이트상 같은 폴더 형태(`manifest.json` + 공백뿐인 `main.js` + README 2벌)로 자신을
선언하고, 각 창 부트스트랩이 그 매니페스트를 **로컬에서 직접**(동적 import,
`src/i18n/packs.ts`) 읽어 첫 페인트 전에 등록한다. 설치 과정이 없다는 점은 그대로다(앱에
함께 실린다). 그 외 언어는 **서드파티 언어팩 플러그인**이 매니페스트
`contributes.translations` 선언으로 제공한다(런타임 등록 API는 없다 — 아래 「언어팩」 절).
서드파티 언어팩도 **코어(Rust)가 설치 매니페스트를 직접 읽어**(스캔 IPC
`list_language_packs`/`read_locale_entries`, `src-tauri/src/plugin_i18n.rs`) 첫 페인트 전에
공급한다 — 중앙 호스트 샌드박스를 거치지 않는다. 이 문서는 지금 코드를 쓸 때 지켜야 하는
규약만 담는다.

왜 en이 정적 시드가 아니라 번들 팩인가: 시드였던 이유는 오직 "서드파티 경로(중앙 호스트
스냅샷)가 비동기라 첫 페인트를 놓친다"였는데, 번들 팩은 부트스트랩이 **직접** 읽으므로 그
지연이 없다. 대신 (1) 사전이 코어 청크에서 빠져(비-eager `import.meta.glob`) ko 사용자는
영어 바이트를 한 번도 받지 않고, (2) en이 다른 언어팩과 같은 형태가 되어 외부 저작자에게
살아 있는 예제가 된다(도그푸딩). 폴더명 규약은 `language-pack-<코드>` — 로더가 **사전을 열지
않고** 폴더 이름에서 코드를 파생해야 "활성 로케일만 로드"가 성립한다(가드:
`src/i18n/packs.test.ts`).

활성 로케일은 `SharedSettings.language`(vault 동기화)에 저장되고, 창 부트스트랩이
`src/i18n/store.ts`의 `setActiveLocale`로 확정한다 — 설정 창 「외형 › 테마」 페이지의
언어 드롭다운에서 바꾼다. `language`가 아직 저장된 적 없으면(최초 실행 등)
`src/i18n/detect.ts`의 `resolveLanguage`가 `navigator.language`로 ko/en을 판정한다(`ko`로
시작하면 ko, 그 외는 en — Rust `src-tauri/src/i18n.rs`의 `locale_to_builtin_language`와 같은
규칙이라 트레이·창 타이틀 등 네이티브 UI와 갈라지지 않는다). 드롭다운 후보는
`availableLocales()`가 돌려주는, **이 창에 등록된** 로케일 전부다(ko 코어 + 번들 언어팩 +
설치된 서드파티 언어팩) — 설정 창은 마운트 때 `loadEnabledBundledPacks`로 **켜져 있는 번들
팩 전부**를, `listLanguagePacks()` + `readLocaleEntries(code)`로 **설치 팩 전부**를
등록하므로(다른 창은 자기가 그릴 언어 하나만 —
`readLocaleEntries(language)`), 서드파티 언어팩이 하나도 없어도 ko·en 둘은 항상 후보에
있다. 번들 팩을 설정에서 끄면 다음 창 로드부터 그 언어가 후보에서 빠진다(이미 그려진 창은
그대로 — VS Code의 "언어 변경은 재시작"과 같은 결).

설치(서드파티) 언어팩은 그 규칙에서 갈라진다: 설정 창을 띄워 둔 채 언어팩 플러그인을
설치·활성·비활성·제거하면 **설정 창이 자신만 리로드해**(`settings.ts`의
`reloadForLanguagePack`) 드롭다운이 그 자리에서 최신이 된다. 위 카탈로그 스캔은 마운트
첫머리 한 번뿐이라 목록만 다시 그려서는 반영되지 않고, 그렇다고 스캔을 호스트 재빌드마다
반복하면 테마·색·일반 플러그인 토글 등 훨씬 잦은 재빌드가 전부 그 IPC 비용을 문다 — 그래서
언어팩이 실제로 오갈 때만 한 번 무는 리로드를 골랐다(언어 피커가 저장 뒤 이 창만 reload하는
것과 같은 선례). 대상이 언어팩이 아닌 설치·토글은 예전처럼 부분 재렌더로 끝난다.

## 규칙

- **사용자 눈에 보이는 문자열**은 코드에 리터럴로 쓰지 않고 `t("키")`
  (`src/i18n/t.ts`)로 조회한다. 원문은 `src/i18n/ko.json`에 둔다.
- 대상은 사용자 노출 문자열만: UI 라벨·placeholder·다이얼로그·토스트 등.
  로그(stderr/console)·주석·개발자 진단·테스트 헬퍼는 대상이 아니다.
- 아직 이관되지 않은 영역(아래 진행 상태)은 기존 리터럴을 유지한다 —
  이관은 영역 단위로 진행하고, 새 코드는 이관된 영역에서만 `t()`를 쓴다.
- **모듈 최상위에서 `t()`를 평가하지 마라**(로케일 확정 전에 굳는다) — 렌더/호출
  시점에 해석한다. 창 부트스트랩은 모듈 import(동기, 항상 가장 먼저) 이후에야
  `setActiveLocale()`을 부르므로, 최상위 `const X = t("...")`는 활성 로케일이
  무엇이든 영원히 ko로 고정된다. 사용처가 렌더 함수 안이면 상수를 함수화
  (`const X = () => t(...)`)하고, id·target처럼 비문자열 필드와 섞인 카탈로그는
  라벨을 `labelKey`로만 갖고 소비 지점에서 `t(item.labelKey)`로 조회한다.
- **긴 안내문(가이드 메모 등)은 문장만 사전에, 구조는 코드에** 둔다
  (`src/note/guide-note.ts`가 「시작 가이드」 메모의 예). 사전 값에 마크다운 기호
  (`- [ ]`·`#` 등)를 넣으면 번역자가 옮기다 그 기호를 깨뜨릴 수 있어, 문장만 담아야
  번역이 안전하다. 문장 안에서 다른 UI 요소(버튼 이름 등)를 가리켜야 하면 그 이름을
  직접 적지 말고 그 요소가 실제로 쓰는 기존 i18n 키를 `{플레이스홀더}`로 끌어와
  채운다 — 그래야 버튼 라벨이 바뀌는 날 안내문도 함께 따라가고, 따로 옛 이름으로
  남지 않는다.

## 키

- 형식: `<영역>.<구성요소>.<이름>` — 소문자, 점 구분.
  예: `panel.search.placeholder`, `panel.list.empty`.
- `<영역>`은 소스 디렉터리와 1:1(`panel`, `note`, `settings`, …).
- `ko.json`은 **평탄한(flat) 키→문장 맵**이며 키를 사전순으로 유지한다.
- 문장이 바뀌어도 키는 유지한다(키는 식별자, 문장은 값). 의미 자체가 바뀌면
  키를 새로 판다.

## 매개변수와 조사

- 동적 값은 `{이름}` 플레이스홀더로 쓴다:
  `"note.restore.done": "{title} 노트를 복원했습니다"` →
  `t("note.restore.done", { title })`.
- 문장은 통째로 키 하나에 담는다. 조각(단어·구)을 코드에서 이어 붙이지
  않는다 — 언어마다 어순이 달라 번역이 불가능해진다.
- 한국어 조사는 **병기**한다: `…을(를)`, `…이(가)`. 조사 자동 판별 로직은
  두지 않는다.

## 폴백

`t(키)` 조회는 **활성 로케일 사전 → ko 사전 → 키 문자열** 순으로 폴백한다
(`src/i18n/store.ts`가 로케일 사전을 보관하고, `src/i18n/t.ts`가 이 순서로 찾아
치환까지 한다). 활성 로케일과 ko 어디에도 키가 없으면 키 문자열을 그대로
반환한다 — 누락이 화면에서 바로 보이게 하기 위한 의도적 동작이다. 활성 로케일이 ko이면
체인의 1·2단계가 같은 사전이라 사실상 한 단계다. en은 번들 팩이 ko.json 전 키를 100%
커버하므로(드리프트 가드: `src/i18n/packs.test.ts`) 2단계까지 갈 일이 거의 없고, 서드파티
언어팩(en 이외의 언어)은 놓친 키(플레이스홀더 불일치·미번역)만 ko로 메워진다.

번들 팩도 서드파티 언어팩과 **똑같이** `validateLocaleEntries`로 ko와 대조해 통과분만
등록된다(`registerBundledLocale`) — 번들이라고 검증을 건너뛰지 않는다. 다만 등록된 코드는
보호 대상이 되어, 이후 같은 코드로 오는 서드파티 `registerLocale`을 무시한다(이슈 #30의
"악의적·실수 언어팩이 앱 내장 번역을 조용히 대체하지 못한다"). ko는 기준 언어이자 검증
base라 **번들 팩으로도** 덮을 수 없다.

## 언어팩 — 최종 구조

언어를 공급하는 경로는 **셋뿐이고, 셋 다 창이 첫 화면을 그리기 전에 끝난다.** 호스트 왕복이
남아 있던 마지막 경로(명령형 `memo.i18n.register` → 중앙 호스트 스냅샷 → 각 창)는 제거됐다.

| 층              | 무엇                                                | 어떻게 창에 들어오나                                             |
| --------------- | --------------------------------------------------- | ---------------------------------------------------------------- |
| ko(기준 언어)   | `src/i18n/ko.json`                                  | 코어에 정적 import — `t()` 폴백 체인의 마지막 사전이자 검증 base |
| 번들 언어팩     | `src/plugin/builtin/language-packs/language-pack-*` | 각 창 부트스트랩의 동적 import(`src/i18n/packs.ts`)              |
| 서드파티 언어팩 | 설치 플러그인의 `contributes.translations`          | 코어(Rust `plugin_i18n.rs`)가 설치 매니페스트를 스캔 → IPC       |

**서드파티 언어팩은 데이터 선언이다.** 매니페스트에 `{locale, label, entries}` 배열을 적으면
끝이고, `main.js`는 비워 둔다(호스트가 샌드박스를 아예 안 띄운다). 코어는 앱데이터
`plugins/` 스캔 결과에서 그 배열을 직접 읽어 IPC 두 개로 공급한다: 카탈로그
`list_language_packs()`(설정 창의 언어 드롭다운 후보)와 사전 `read_locale_entries(locale)`
(각 창이 자기가 그릴 언어 하나). 이 구조가 VS Code가 언어팩 확장을 확장 호스트 없이 코어에서
읽는 것과 같은 결이고, 콜드 스타트에서 서드파티 언어가 리로드 깜빡임 없이 곧바로 뜨는 이유다.

**수집 게이트는 네 조건이다**(`plugin_i18n.rs`의 `may_contribute_translations`). 언어팩이
브리지를 타던 시절 실제로 통과해야 했던 조건을 그대로 옮긴 것이라, 경로가 바뀌었어도 통과
집합은 같다:

1. **활성(enabled)** — 꺼 둔 플러그인은 중앙 호스트도 실행하지 않았다.
2. **현재 OS 지원(`platforms`)** — 미지원 OS의 플러그인도 실행하지 않았다. 언어팩만 이 규칙에서
   빠지면 `platforms: ["windows"]`인 플러그인이 macOS에서 버튼 하나 못 붙이면서 UI 언어는
   갈아치우는 상태가 된다.
3. **`kind: "capability"`** — 능력 제공의 공통 게이트(theme/background/font와 같다).
4. **`i18n` 권한 선언** — `i18n`은 저위험이라 **선언만으로** 통과한다. 코어도 `granted`를
   요구하지 않는다(요구하면, 저위험 권한을 부여 목록에 넣지 않는 정상 설치 언어팩이 전부
   거부된다).

넷 중 하나라도 어긋나면 **오류 없이 그냥 수집되지 않는다** — 저작자용 표면화는
`npm run plugin -- lint <폴더>`가 맡는다(같은 네 조건을 설치 전에 재현한다). 항목 하나의
형식 위반(`locale`이 대문자, `label`이 공백, `entries`가 맵이 아님, 직렬화 256KB 초과)은
**그 항목만** 조용히 건너뛴다 — 한 팩의 실수로 다른 언어팩 사용자까지 언어를 잃지 않게.

**병합과 보호.** 같은 로케일 코드를 여러 팩이 공급하면 플러그인 id 사전순으로 뒤가 앞을 키
단위로 덮는다(LastWins — 코어의 `read_locale_entries`와 프런트 `registerLocale`이 같은
규칙이라 두 경로가 같은 사전을 낸다). **`ko`와 "활성 번들 팩이 등록한 코드"(기본 상태의
`en`)는 서드파티가 덮을 수 없다** — `store.ts`의 `PROTECTED_CODES`가 막는다. 단 사용자가
번들 en 팩을 **끄면** 그 코드는 보호에서 풀리므로 커뮤니티 영어팩이 그 자리를 채울 수
있다(의도된 의미론: 내장을 끄고 대체하는 것은 허용, 조용히 덮어쓰는 것은 금지).

**콘텐츠 검증은 소비 시점**(각 창의 `store.ts` → `validateLocaleEntries`)이다 — ko에 없는
키와 `{플레이스홀더}` 집합이 ko 문장과 다른 값은 그 키만 버려진다. 기준 사전 ko가 프런트
자산이라 백엔드가 미리 구울 수 없고, 그래야 언어팩 하나의 실수가 등록 자체를 막지 않는다.

**언어 변경이 전파되는 경로.** 설정 창 언어 드롭다운 → `SharedSettings.language` 저장 →
설정 창은 스스로 `location.reload()`(이미 DOM에 박제된 트리 라벨·탭 이름까지 바꿔야 해서
부분 재렌더로는 부족하다), 노트·패널 창은 `EV_NOTES_RELOAD` → 중앙 호스트 재빌드 →
`EV_HOST_UPDATED` → 전체 리로드. 새 로드의 부트스트랩이 새 언어의 팩을 다시 읽는다. 중앙
호스트 창만은 숨김 상주라 리로드가 없어, 매 재빌드가 `resolveHostLocale`
(`src/bootstrap/plugin-host.ts`)을 다시 태워 그 창의 사전 등록과 활성 전환을 함께 끝낸다 —
**그 함수가 호스트 창 로케일의 단일 소유자다.** 번들 팩 토글(`set_builtin_enabled`)도 같은
재빌드 체인을 타는데, 이 체인이 곧 "언어 관련 변경이 즉시 전파되는 메커니즘"이므로
언어팩이 호스트를 거치지 않게 된 뒤에도 **유지한다**(근거는 `src/i18n/packs.ts` 주석에 있다).

체인의 마지막 고리는 이제 **조건부**다: 노트 창은 `EV_HOST_UPDATED`를 받으면 새 스냅샷·설정을
예전 것과 비교해 제자리 반영으로 충분하면 리로드하지 않는다(`bootstrap/host-update-plan.ts`).
언어팩은 스냅샷에 아무 흔적도 남기지 않으므로 비교로는 절대 잡히지 않는다 — 그래서 언어와
관련된 재빌드는 발신 쪽이 사유 `"locale"`을 실어 보내고(언어 드롭다운 저장·`flushNotesReload`·
번들 언어팩 토글), 판정기가 그 사유를 **언제나 리로드**로 못박는다. 언어 관련 경로를 새로
추가할 때는 그 사유를 함께 실어야 한다 — 빠뜨리면 열린 창이 옛 언어로 남는 무음 실패가 된다.

**API 축소(breaking).** `memo.i18n.register`는 제거됐다. 마이그레이션 안내는 `host.ts`의
`REMOVED_CALLS` 한 곳에서 나와 **두 표면**에 실린다:

- **런타임** — 옛 이름을 부르면 `UNKNOWN_CALL`로 떨어지고, 오류 문구가 "`entries`를 그대로
  `contributes.translations`로 옮겨라"를 알려 준다(새 오류 코드를 만들지 않는다: 저작자가
  분기할 대상이 아니라 읽을 안내다).
- **CLI** — `memo-plugin lint`가 코드에 남은 옛 호출을 `REMOVED_CALL`(error)로 잡고 같은
  안내를 준다. 저작자가 가장 먼저 돌리는 도구라, 여기 배선이 없으면 앱을 띄워 진단 채널을
  열어 본 사람만 옮길 곳을 알게 되고 lint는 "오타이거나 아직 없는 API"라는 틀린 추측을 준다.

그 이름이 되살아나면 `REMOVED_CALLS`에서 지워야 한다 — 살아 있는 어휘와의 교집합이 0임을
`drift-guards.test.ts`가 고정하므로, 잊으면 테스트가 먼저 운다.

읽기 전용 introspection인 `memo.i18n.locale()`은 그대로 남는다(권한 불필요 — 언어팩과는
이름 네임스페이스만 같은 별개 호출이다).

계약 전문은 `docs/plugin/manifest.schema.json`의 `contributes.translations`, 사람용 설명은
`docs/plugin/authoring.md`의 「언어팩」 절. 축약 템플릿은
`docs/plugin/examples/language-pack-en/`, 실전 크기의 완성형은 번들 팩
`src/plugin/builtin/language-packs/language-pack-en/`이다.

**플러그인 자기 로컬라이즈(메커니즘 + 번들 적용 완료, 축 2 종료).** 언어팩(위 절)은 **앱 내장**
UI 문자열을 다른 언어로 번역하는 경로고, 이 절은 **플러그인 자신이 매니페스트에 쓰는**
문자열(`name`·설정 라벨 등)을 로컬라이즈하는 별개 경로다(축 2, VSCode의 package.nls 방식과
같은 결). 세 부분:

1. **manifest `nls` + `%키%`.** 매니페스트에 선택 필드 `nls: Record<로케일 또는 "default",
Record<키, 문장>>`을 두면, `name`·`summary`·`settingsCategory`·`settingsDescription`·
   `settings[]`의 사용자 노출 필드(`label`·`description`·`placeholder` 등, `options`의
   문자열 축약형은 제외 — 저장 값 보호)가 정확히 `%키%` 형태일 때 활성 로케일 사전 →
   `default` 사전(nls를 쓰면 필수) → 원문(`%키%` 노출, 누락 가시화) 순으로 해석된다. 해석은
   설치(사이드로드) 플러그인의 목록/상세 데이터를 IPC로 받아온 **직후 한 번**
   (`src/plugin/manifest.ts`의 `resolveInstalledPluginNls`, 소비처는 `main.ts`의
   `listPlugins` 배선) — 렌더 지점마다 다시 해석하지 않는다. `nls` 없는 매니페스트는
   100% 무변화. Rust `parse_manifest`가 형태(객체 중첩·leaf 문자열·`default` 필수)를
   동형 검증하고 원문을 그대로 나른다(콘텐츠 해석은 프론트 전담 — 창마다 활성 로케일이
   달라 백엔드가 미리 구울 수 없다). 대상 필드 전수·저작법은 `docs/plugin/authoring.md`의
   "플러그인 자기 로컬라이즈" 절.
2. **`memo.i18n.locale()`.** 활성 로케일 코드를 읽는 읽기 전용 브리지 호출(권한 불필요 —
   `runtime.info()`의 `os`와 같은 실행 환경 introspection). 중앙 호스트가 `build()`/단일
   핫리로드마다 캐시를 갱신해 주입하므로 값은 "이번 빌드 시작 시점" 기준이다(다음
   재빌드 전까지 안 바뀜 — `hostVersion`·`os`와 같은 캐싱 결).
3. **`README.<locale>.md`.** 설정창 상세 뷰가 README를 읽을 때 활성 로케일과 일치하는
   변형을 먼저 찾고, 없으면 `README.md`로 폴백한다(Rust `read_plugin_readme`의 `locale`
   인자, TS `readPluginReadme(id, locale)` 미러).

**번들(내장) 플러그인도 같은 세 경로를 탄다.** 폴더가 앱 소스 트리 안에 있다는 점만 다를 뿐
(`src/plugin/builtin/plugins/*`·`src/plugin/builtin/themes/*`·
`src/plugin/builtin/language-packs/*`), 저작 규약과 소비 지점의 성격은 사이드로드와 동형이다.
앞의 둘은 `src/plugin/builtin/index.ts`가 **eager** 글로브로 모으고(그 목록이 곧 중앙 호스트의
실행 대상이다), 언어팩은 호스트가 실행하지 않는 데이터 선언이라 `src/i18n/packs.ts`가 **비-eager**
글로브로 따로 모은다(사전 바이트를 공용 청크에 넣지 않기 위해):

- `src/plugin/builtin/plugins/*/manifest.json` 전수가 사용자 노출 문자열(`name`·`summary`·
  설정 스키마 라벨 등, `settingsCategory`는 식별자라 제외)을 `%키%` + `nls`(`default`=기존
  한국어, `en`=영어)로 싣는다. 해석기는 `src/plugin/builtin/index.ts`의
  `resolveBuiltinPluginNls`/`resolveBuiltinThemeNls` — `resolveInstalledPluginNls`가 쓰는
  `resolveSettingFieldNls`를 그대로 재사용해 두 경로(설치·번들)가 같은 규칙으로 해석된다.
  소비 지점은 `settings/settings.ts`의 번들 목록(`renderBuiltinList`)·설정 페이지
  (`pluginPages`) — 둘 다 호출 시점의 `activeLocale()`로 해석한다(`BUILTIN_PLUGINS` 배열
  자신, 즉 `import.meta.glob` eager 평가 시점에는 **절대** 해석하지 않는다 — 그 시점은 로케일
  확정 전이다).
- **README 로케일 변형도 번들에서 동작한다.** `import.meta.glob`이 `README.md`뿐 아니라
  `README.*.md`도 모아(`loadFolder`가 파일명에서 로케일 코드를 뽑는다) `BuiltinPlugin`/
  `BuiltinTheme`의 `readmeLocales`에 싣는다. 소비 지점(`pickBuiltinReadme`, 역시
  `settings.ts`의 목록·상세 렌더)이 활성 로케일 → 기본 `README.md` 순으로 고른다(Rust
  `read_plugin_readme`의 로케일 우선순위와 같은 결 — 다만 번들은 이미 빌드에 다 들어있어
  IPC 없이 동기로 고른다). 도그푸딩 실증으로 `font`·`copy-ai-prompt`에 `README.en.md`를
  붙였다 — 나머지 번들 README 영어판은 콘텐츠 작업(메커니즘은 이미 전부 열려 있다).
  번들 언어팩도 같은 규칙을 따른다(`packs.ts`가 `README.*.md`를 `readmeLocales`로 모으고,
  `packToBuiltin`이 그대로 설정창 목록에 넘긴다 — 언어팩이야말로 영어 README가 없으면 정작
  그 언어 사용자가 읽을 수 없어서 두 벌이 필수다, 가드: `src/i18n/packs.test.ts`).
- **런타임(main.js) 사용자 노출 문자열**(토스트·버튼 툴팁·pickList/prompt 타이틀 등)은
  플러그인 안에 작은 `{ ko: {...}, en: {...} }` 사전을 두고 `memo.i18n.locale()`(무권한,
  캐시된 값)로 활성 로케일을 한 번 읽어 고른다 — 등록을 그 뒤로 미루는 정도의 코드 변화만
  필요하다(`copy-ai-prompt`·`duplicate`·`font-scale`·`font`·`reset-options`·`word-count`·
  `template` 적용, `highlight`·`spoiler`·`kbd`·`underline`·`superscript`·`wikilink`·
  `all-desktops`·`always-on-top`·`background`·`transparency`는 진단 로그 말고는 사용자
  노출 문자열이 없어 대상 밖). 진단(`memo.runtime.log`)은 저작자용이라 로컬라이즈 대상이
  아니다. 플러그인마다 이 작은 사전+헬퍼를 각자 인라인으로 갖는다 — 샌드박스 코드는 모듈
  `import`가 불가능해(각 `main.js`가 독립 origin에서 `new Function`/`<script src=blob:>`로
  실행된다) 공유 런타임 모듈을 강제할 수 없고, 각 플러그인 독립 원칙과도 맞다.

**완료.** Rust 내장 언어 테이블(트레이·업데이터·창 타이틀·환영 노트; 서드파티 언어팩
범위 밖)은 `src-tauri/src/i18n.rs`에 ko/en 두 벌로 있다(이슈 #29). `language` 미설정 시
OS 로케일로 ko/en을 판정하는 규칙(`locale_to_builtin_language`)은 이 문서 위쪽의
`resolveLanguage`(TS)와 같다.
